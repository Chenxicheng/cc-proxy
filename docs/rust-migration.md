# Rust migration specification

## Product boundary

`claude-adapter` 2.0 was a CLI product. One self-contained npm package owned offline installation, configuration prompts, embedded native binary selection, Claude settings updates, startup feedback, and signal forwarding. The Rust binary owned the listener, validation, upstream HTTP, Anthropic/OpenAI conversion, SSE, tools, usage/error storage, and runtime logging. There was no Node proxy fallback or JavaScript library API.

New installations store configuration in `~/.cc-proxy/`. If `~/.claude-adapter/` already exists, cc-proxy continues using that legacy directory, and its existing `config.json` shape and CLI flags remain valid. Credentials use exactly one of the existing plaintext `apiKey` field or `apiKeyEnv`, which stores only a portable environment variable name. Rust resolves environment-backed credentials once at startup from the inherited process environment and never persists the value. The native process receives `--config <absolute-path>` and `--port <preferred>`, binds the first available loopback port, then prints one `CC_PROXY_READY=<json>` line after the listener is active. Node forwards Unix signals directly; on Windows it requests the same graceful drain through the child stdin pipe before using the 10-second forced-stop fallback.

## Protocol requirements

- Preserve `/health`, `POST /v1/messages`, CORS, Anthropic error envelopes, model-family options, tool ID repair, response/SSE event order, and usage schema version 2.
- Accept request bodies up to 32 MiB and at most 128 in-flight requests.
- Reuse one upstream HTTP client. Downstream polling must drive upstream polling so slow readers apply backpressure and disconnects cancel upstream work.
- Treat `main@8a19608` as the request-conversion oracle. Rust must emit the same Chat Completions JSON fields and role/block mapping as the TypeScript 1.2.2 converter before adding any Rust-only protocol behavior.
- Match the TypeScript transport contract: JSON `Accept`/`Content-Type`, bearer authorization, explicit `stream`, and unchanged forwarding of configured upstream headers, including `User-Agent` and provider-specific headers.
- Skip contentless hook messages, retain the narrow short-token filter only for non-terminal assistant history, map non-user string/array turns as assistant history, and preserve the TypeScript tool ID repair and tool-result ordering behavior.
- Tools and tool choices follow the TypeScript converter exactly. Rust-only validation must not reject fields that TypeScript accepted or add fields that TypeScript did not send upstream.
- User image blocks map to Chat `image_url` parts; tool-result images follow the text tool messages in a labeled user message because Chat tool messages cannot carry images. Unsupported sources return `400`.
- Use `max_completion_tokens` only for GPT-5 and OpenAI o-series models and `max_tokens` elsewhere; retain the Azure minimum-token adjustment. Do not forward `metadata.user_id`. Map `output_config.effort` only for recognized OpenAI reasoning models and preserve existing GLM/Qwen model-family behavior, including tool-turn reasoning history. Reject explicit `output_config.format` until structured output mapping is supported.
- Forward the same optional fields as TypeScript and ignore unconverted provider extensions. Request validation protects required shapes but does not invent stricter upstream constraints.
- Restore main@8a19608 response and SSE behavior, including `reasoning_content || reasoning` as thinking blocks. Do not invent cryptographic signatures or log reasoning text. Reasoning-only completions are valid.
- Preserve a content-free `stop` as the legal Anthropic `content: []` / `end_turn` result and record it as `empty_end_turn`; do not synthesize content or convert it to an API error. Keep task-level acceptance separate so text/tool E2E scenarios still fail when no requested output was produced.
- Treat terminal assistant prefill as a protocol-capability boundary. Standard Chat Completions has no portable equivalent, so `upstreamCapabilities.assistantPrefill` defaults to `unsupported` and rejects the request locally with an actionable `400` before upstream I/O. `continue_final_message` preserves the terminal assistant content and adds exactly `continue_final_message: true`; `native` preserves it without an extension. Never delete terminal prefill content, synthesize a continuation prompt, infer support from the base URL/model, or retry through a different mode.
- Allocate consecutive Anthropic block indices exactly once; route interleaved tool deltas by upstream index. Text following tools is emitted immediately in a new block. Each block stops exactly once.
- Accumulate tool names against the request's declared names. Start a tool immediately on an exact, unambiguous match; defer only ambiguous names until finish_reason or [DONE]. Accept repeated identical names after block start, reject changed or undeclared final names. Append arguments unchanged and validate the completed JSON object; absent arguments mean {}.
- On finish_reason, close content blocks but keep reading final usage. [DONE], or clean EOF after finish_reason, emits one message_delta and message_stop. [DONE] without finish_reason may infer tool_use/end_turn only for complete content. EOF without either terminator and transport errors fail without successful message_stop.
- Skip empty choices and accept usage-only or content-free choice tails after finish_reason, including a repeated identical finish_reason. Reject later content or a conflicting finish_reason. Preserve refusal handling and map length to max_tokens consistently. Index reuse, fragmented names, missing block stops and main's streaming length mapping are documented parity exceptions.
- Match main client usage: numeric zero placeholders at message_start; final output_tokens defaults to zero, input_tokens is omitted without token counters; non-streaming counters default to zero. Raw JSONL usage still distinguishes missing values from actual zeroes. Do not subtract cached or reasoning tokens from upstream totals.
- Use eventsource-stream 0.2.3 for upstream SSE framing and Axum Sse/Event::json_data for downstream encoding. Keep reqwest, Tokio, bytes and serde_json; do not add retrying POST wrappers or alternative JSON engines.
- Apply fixed streaming deadlines without changing non-streaming requests: 120 seconds for response headers, 120 seconds from headers for first non-empty body bytes, 240 seconds from the same headers for the first emitted Anthropic event, and 300 seconds per later raw-body read while downstream polling is active. Header timeout is HTTP 504; body or event timeout is one SSE api_error with no successful terminal events. Comments, pings, partial bytes and empty frames do not count as the first Anthropic event. Do not pre-read or replay body bytes, retry POSTs, spawn an upstream drain task, or synthesize heartbeats.

## JSONL storage

Usage and error records use a bounded Tokio channel with capacity 1024. The request path uses `try_send` and never waits for disk. One writer task keeps buffered daily usage and error files open, rotates at the UTC date boundary, flushes after 64 KiB or one second, and drains on graceful shutdown. A full queue drops observability records, increments a counter, and emits a coalesced warning. JSONL is observability data, not an audit or billing ledger. Successful records classify the response `outcome` as `usable` or `empty_end_turn`; the latter is written even when the upstream omitted usage.

For an upstream non-success response, error JSONL retains the status and response body plus a sanitized `upstreamRequestShape`. The shape includes only sorted field names, message count and roles/content types, token-field choice and numeric value, tool count/function field names, tool-choice kind, model family, stream mode, and whether a thinking option is present. It never contains prompts, tool arguments or schemas, image data or URLs, headers, or API keys.

The manual real-upstream artifact uses internal `schemaVersion: 3`. Its transparent probe records one sanitized entry per request: request sequence and shape (including whether it ends in an assistant prefill), HTTP status, raw-body chunk/SSE event counts, `[DONE]` versus EOF, finish reasons, numeric usage fields, known delta counts, unknown delta field names, output-kind flags, and the classified outcome. It forwards the original bytes unchanged and never persists request bodies or response text.

## Baseline and acceptance

A deterministic local upstream and shared fixtures compare Node 1.2 behavior with Rust. Benchmark concurrency is 1, 10, 50, and 100, with warm-up followed by five measured runs. Results record throughput, errors, p50/p95/p99 latency, first actual content latency, CPU, and RSS. Rust must preserve supported behavior and show a repeatable improvement in throughput, latency, or resource use without a material regression elsewhere.

`bench/baseline-2026-09-19.json` preserves the pre-cutover Node/Rust comparison. The current harness also runs tools, reasoning, upstream-error, slow-reader, and downstream-disconnect preflights before collecting text and SSE performance samples; `BENCH_UPSTREAM_DELAY_MS` controls deterministic upstream delay.

The release embeds macOS Intel x64, macOS Apple Silicon arm64, Linux glibc x64, and Windows x64 binaries. Linux arm64, musl, Windows arm64, Responses API, N-API, and automatic model switching are out of scope. User images are converted to Chat `image_url` parts when the upstream model supports image input.

Real LM Studio/Qwen acceptance runs a fixed six-case matrix: minimal streamed text without tools, the exact streamed Claude Code text request, the same request non-streaming, a minimal Read tool with `tool_choice=auto`, the same tool with a named choice, and the complete Claude Read/tool-result/final-text loop. The diagnostic run explicitly uses `assistantPrefill: native` so it measures the upstream's behavior without changing LM Studio model configuration. Text and Read require real output events and reject `empty_end_turn`, while protocol fixtures separately prove that legal empty completions remain consumable and that the default unsupported mode performs no upstream I/O.

Release CI builds and tests macOS Intel x64, macOS Apple Silicon arm64, Linux x64, and Windows x64 binaries, bundles them with all production JavaScript dependencies into one `cc-proxy-<version>.tgz`, verifies an empty-cache `npm install --offline`, and creates the GitHub release without publishing to npm automatically.
