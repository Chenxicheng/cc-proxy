cc-switch 与 claude-adapter
Request / Response 转换对比

代码快照：cc-switch f2537fd；本项目 63a66b6 加当前工作区修改。范围：Claude Code 的 Anthropic Messages 请求，经 OpenAI Chat Completions 或 Responses 上游，再转换回 Anthropic 响应。2026-09-23。

结论：cc-switch 胜在协议覆盖、多模态与供应商适配；本项目胜在 Chat Completions 单一路径的输入校验、失败可见性和流终止约束。若只评估共同的 Chat 流式转换，我更推荐本项目的处理方式；两者没有同条件性能实测，不能给出速度排名。

cc-switch

主要优点
  • 同一 Claude 入口支持 Chat Completions、Responses、Gemini 等格式；Responses 路径处理 reasoning 回传和 hosted tools。
  • Chat 路径支持普通图片，并把 tool_result 图片转成后续 user 消息；工具 schema 会做上游兼容清理。
  • 流式 usage 等待末尾统计，处理重复 finish_reason；客户端 usage 可拆分缓存 token。
主要不足
  • Chat 非流式工具参数 JSON 解析失败会回退为 {}；未知结束原因回退为 end_turn，可能隐藏上游协议问题。
  • 覆盖多个协议和供应商，使转换行为依赖路由与 provider 选项，定位问题需要跟踪更多分支。

claude-adapter

主要优点
  • Request 先校验必需字段和内容结构；Response 对 malformed tool arguments、缺失 tool name、未知结束原因返回明确错误。
  • SSE 对并行工具、分片名称、完整 JSON 参数、结束信号建立明确约束；错误流不会再发送成功结束事件。
  • 遵守旧版 TypeScript 的 Chat 请求 wire shape，并保留 GLM/Qwen 的已选参数，行为边界容易验证。
主要不足
  • 只支持 Anthropic Messages ↔ Chat Completions；图片及工具结果图片直接返回 400。
  • 不清理工具 JSON schema；客户端 usage 只返回 input/output，总缓存明细保留在内部 JSONL。

逐项比较

转换点cc-switch：优势与代价本项目：优势与代价对用户的影响
协议与模型参数按 provider 走 Chat、Responses 或其他转换；Responses 能映射 reasoning.effort，并处理无状态 reasoning 回传。路由与选项更多。[1][2]只生成 Chat Completions；针对 GPT/o-series、GLM、Qwen 映射 max_tokens、thinking、reasoning_effort。不能直接接仅支持 Responses 的上游。[5]选模型更灵活时 cc-switch 有利；上游限定为 Chat 时，本项目的协议边界更清楚。
Request 校验Chat 转换对缺失 model、messages、max_tokens 多处采用跳过或默认；可容纳宽松输入，但错误可能延迟到上游。[1]校验必需字段、数值范围及块结构，图片明确拒绝；不支持的字段大多不转发。[5]本项目更快指出请求结构问题；cc-switch 对非标准网关较宽容。
消息、图片与工具结果支持图片 URL/base64；Chat 无法在 tool 消息中放图片时，将图片移至后续 user 消息。可用性更强，但消息角色与原始顺序语义可能变化。[1]文本与工具结果按既有 TypeScript 路径转换；图片返回 400，避免静默丢失但阻断视觉任务。[5][7]需要截图或图像工具结果的 Claude Code 工作流，目前应优先考虑 cc-switch。
Tools 与 schema过滤特定内部工具、补齐根 object schema 并移除 format: uri；更易通过挑剔的上游，但转换后的 schema 不再完全等同输入。[1]只映射 name、description、input_schema，不做 schema 修正；形状可预测，上游不接受 schema 时需显式修复。[5]cc-switch 接入面更广；本项目更方便确认实际发送了什么。
非流式 Response支持文本、reasoning、tool calls、旧式 function_call；但 malformed arguments 可退化成空对象，未知 finish_reason 可映射为成功结束。[1]严格检查 assistant、单个 choice、tool name/arguments 与 finish reason；不符合契约返回 502。拒绝响应另有 refusal 标识。[6]本项目减少“工具实际坏了却显示成功”的风险；cc-switch 对格式不规范的上游容忍度较高。
流式 Response / SSE按上游 index 聚合并行工具，缓存结束事件等待最终 usage，允许重复 finish reason；Chat 路径的未知 finish reason 仍降级为 end_turn，工具参数片段未在结束前做完整 JSON 校验。[3]校验完整工具参数和结束信号；不完整 SSE 或传输错误发 error，不发成功终止事件。对非标准流容忍度较低。[7]本项目更适合要求工具结果可追责的场景；cc-switch 更适合格式参差的网关。
Usage / 缓存在 Anthropic 响应中拆分缓存读写 token，避免把缓存命中重复算作新输入；流式等待尾部 usage。[1][3]客户端 usage 只映射 input/output；内部 JSONL 保留 cache/reasoning 明细，缺失客户端计数默认 0。[6][8]cc-switch 对客户端侧 token 展示更完整；本项目需要查内部记录才能核对缓存。

流式返回专项：哪个更好？

共同的 Claude → OpenAI Chat → Claude 场景：本项目的协议正确性更好。它检查每个 SSE JSON、工具参数完整性和成功终止条件；cc-switch 对重复结束事件及末尾 usage 更宽容，但 Chat 路径会跳过无法反序列化的 chunk，并把未知 finish_reason 当成 end_turn。如果比较“可接多少种上游”，cc-switch 更强；如果比较“同一流是否会把坏结果报成成功”，本项目更稳。[3][7]

流式处理点cc-switch Chat 路径本项目 Chat 路径判断
首个内容与背压从 bytes_stream() 逐块读，转换事件后立即 yield；正常情况下无需等完整响应。原生 Anthropic 路径还能直接透传。[3][4]bytes_stream() → eventsource → Axum SSE；逐事件输出，慢下游通过轮询链路限制继续读取上游；有首内容提前送达测试。[7]两者都是增量处理；源码不足以证明谁的首 token 更快。原生透传是 cc-switch 的额外优势。
SSE 解析与开销字节先拼入 UTF-8 String，查找块分隔符并 drain，再解析为类型化 chunk；每个下游事件单独格式化。大块、高频事件可能增加扫描和拷贝，属于源码推断。[3][4]使用 eventsource-stream 做帧解析，再转为 serde_json::Value、构造事件 Vec 并序列化；这些步骤同样有分配开销。[7]不能凭代码行数或解析库选择推断吞吐。优化前应测 CPU、分配量、p95 和首内容延迟。
工具调用用上游 index 维护并行工具；支持先收到 arguments、后收到 ID/name，并在 finish 时补发块。没有看到 Chat 路径在成功结束前验证参数是完整 JSON 对象。[3]也按 index 处理并行工具；工具名分片时仅等待名称可判定，参数在关闭块前解析并检查必须为 JSON 对象。[7]本项目更早发现不可执行的工具调用；cc-switch 对缺字段上游更有容错能力。
结束与错误缓存一个 message_delta 等 usage，容忍重复 finish；自然 EOF 且已有 pending delta 可正常结束。无法反序列化的 Chat chunk 会被跳过。[3]同样等尾部 usage、容忍相同 finish；EOF 缺终止信号、相冲突的 finish、完成后新增内容或坏工具参数都会输出 error，不发送成功终止。[7]本项目的失败语义更可靠；cc-switch 对非标准流完成方式更宽容。
功能广度另有 Responses SSE 状态机、web search 和 reasoning 转换；需要更多状态、缓冲和测试。[9]仅 Chat Completions SSE，范围集中。[7]多供应商使用 cc-switch 更方便；单一 Chat 路径更适合本项目当前目标。

性能证据与可执行的比较方法

已测量，但不是 cc-switch 对比：本项目历史基准使用同机、release 构建、确定性本地 mock upstream、预热后 5 次中位数。流式并发 50 时，Rust 为 8658.75 请求/秒、p95 7.68 ms，旧 Node 为 3742.50 请求/秒、p95 14.60 ms；并发 100 时分别为 9034.03 / 14.30 ms 和 4515.07 / 23.23 ms。并发 1 时 Rust 为 419.22 请求/秒，低于 Node 的 559.25。该结果只说明 2026-09-19 的 Rust 与旧 Node 比较，不代表当前代码与 cc-switch 的差距，也不代表真实模型延迟。[10]

性能排名：目前无法判定。要回答“哪个更快”，应固定同一台机器、同一 mock 上游、同一 Chat 请求和 SSE 分块，分别运行两边 release 二进制；覆盖短文本、长文本、并行工具、慢读取和断连，在并发 1/10/50/100 下记录首内容延迟、吞吐、p95/p99、CPU、RSS、错误数。Responses 和原生透传需另列场景，不能混入共同 Chat 路径。若结果表明本项目的事件分配是瓶颈，再针对该热点优化；目前没有依据为性能而移植 cc-switch 的手写 SSE 解析。[11]

建议优先级

  1. 先补图片输入：这是当前项目最明确的用户功能缺口；需要定义 tool_result 图片的角色与顺序语义，然后用真实上游验收。
  2. 按上游故障证据决定 schema 清理：借鉴 cc-switch 的具体规则，不要无条件改写工具 schema。
  3. 只有目标上游确需 Responses 时再扩协议：这会新增独立的 Request、Response、SSE 契约，不能当作几个字段的补丁。
  4. 保留严格错误边界：不照搬 malformed arguments → {} 或未知结束原因 → end_turn 的成功回退。
